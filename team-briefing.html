Runbook, the Apple setup

What Scribl said

"We don't have anything." -- Eric Rice, 00:48:15

"I'm happy to go through and do the work on it. I'm just pointing me in the right direction" -- Eric Rice, 01:02:47

Scribl has no Apple accounts today and Eric is doing the signup himself, so this is his work. What follows is what we already know about the path, written to save him the hour of starting cold. It is not a checklist we filled in on his behalf.

Our initial research

The D-U-N-S number is the critical path. Apple will not enrol an organisation without one, and no Apple Developer account means no signing identity, no TestFlight, and side-loading only. Start it first.

One practical note on the D-U-N-S, because a mismatch is the usual cause of a rejection. The legal entity name, the registered address, and a public website on a domain Scribl owns all have to line up with Scribl's incorporation records. Apple has its own lookup for an existing number, and a fresh request can take several business days, longer if Dun and Bradstreet comes back with questions.

Enrolment goes in as an organisation, not an individual, because the account has to outlive any one person and the app needs to show Scribl as the seller. The Account Holder is one person and the role cannot be shared. Only that person can accept new Apple agreements or change the membership, so if they go quiet the whole account can stall.

In App Store Connect, seats go at Developer or App Manager. Nobody outside Scribl needs Admin or Finance. The bundle identifier is permanent and reverse-DNS, built from a domain Scribl controls. We have deliberately not guessed Scribl's domain here.

Signing needs a distribution certificate and a provisioning profile. An App Store Connect API key is what lets a build pipeline upload to TestFlight with no person at a keyboard.

Internal TestFlight testers get builds with no Apple review. External testers trigger Beta App Review, which takes time and can come back with changes required. That is the timing risk for the mixed-platform beta group Matthew Kaplan raised.

What we are asking Scribl for

  • A named owner and a date on the enrolment. That date is what tells us when signing and TestFlight become possible.
  • The D-U-N-S number, or the date it was requested. Either one closes the biggest open risk on the timeline.
  • The Account Holder's name, and a second person at Scribl who knows it. That role cannot be shared, so we need to know who has to stay reachable.
  • The exact bundle identifier string. We register that string and nothing else, because it cannot be changed once an app record exists.
  • App Store Connect invitations at the roles above, once we send the email list. Accepted invitations are what let our engineers build and upload.
  • A yes or no on the API key. Yes means the pipeline uploads on its own. No means a person with the account credentials does every upload by hand.
  • The names and emails of the first internal TestFlight testers. With those, a build reaches them the same day it finishes processing.

If any of this does not fit how Scribl works, say so and tell us what does. We can plan against a counter-proposal. We cannot plan against silence.

Runbook, AWS deploy access

What Scribl said

Eric Rice confirmed at kickoff that Scribl already has an AWS account hosting the B2B game (00:45:38 to 00:46:01). What the room did not settle is whether we deploy the D2C app into that existing account or into a new one (00:46:01 to 00:47:44). Rob is taking that question to Bounteous's AWS side and following up with James, Scribl's AWS contact, and Bhasin, the technical contact James would loop in.

Our initial research

We read the B2B infrastructure code before asking anything, so we would ask a specific question instead of a vague one. The CDK app declares four environment stages, Dev, Poc, Stg, Prod, plus an ad hoc Sandbox, but only Dev, Poc, and Prod carry sizing config, so Stg and Sandbox inherit Dev sizing. The deploy workflow (deploy.yml) runs on workflow_dispatch only, and its environment input offers exactly two choices, QA and Stg. Those map to the CDK stacks Scribl-Poc/Infrastructure and Scribl-Stg/Infrastructure. Prod exists in the CDK code with no deploy job. The workflow assumes AWS_QA_ROLE_ARN or AWS_STG_ROLE_ARN through GitHub OIDC, and pins us-east-1 throughout. So their own team ships on two environments, not three, whatever the stack names suggest.

OptionWhat Scribl doesWhat it gives usTrade-off
Cross-account IAM role Creates a role in their account that trusts our AWS account, scoped to the permissions we enumerate Fastest to set up, easiest to revoke, keeps their account boundary intact, their team has already set up a role-assumption trust for the B2B deploy, so the shape is familiar Our workloads run inside their account, so their billing and their guardrails apply to us, and every permission we need has to be listed up front
Dedicated account in their AWS Organization Creates a new account inside their organization and wires its guardrails, then grants us access to that account only Clean blast radius, clean cost attribution, nothing we do can touch the B2B product Someone at Scribl has to create the account and set up its guardrails, more work up front and needs an owner
Their existing CDK path Adds our stacks to the same CDK app and shape, then runs the same deploy pipeline for both products Reuses what their team already knows, keeps one deployment story We inherit their patterns, and our release schedule has to move with theirs

This is a recommendation, not a decision. The dedicated account is the cleanest path if someone at Scribl will own creating it. The cross-account role is the right answer if we need to move this week. Rob is checking both with Bounteous's AWS side and with James and Bhasin before either is locked in.

One thing we will not carry over. The B2B API applies schema changes on every container start, with no versioned migration chain and no gate. We will author versioned migrations for the D2C app instead.

What we are asking Scribl for

Six things. Put a named owner and a date on the first one, because the rest follow from it. Each line says what it unblocks.

  • A decision on the existing account versus a new one, with a named owner and a date. Scribl decision That locks one row of the table above and setup starts.
  • The AWS account id we deploy into. Scribl decision That id goes straight into our CDK config.
  • The AWS region, stated explicitly. Their B2B pipeline deploys to us-east-1 and our POC database is in us-east-2, so this is a real question rather than a formality. The answer is pinned across our CDK stacks and our deploy workflow.
  • The name and contact for whoever can create an IAM role or an organization account. Scribl decision We send that person a least-privilege policy scoped to what the D2C app needs, rather than a copy of the B2B product's full permission set.
  • The approval path for a permission change, and how long it takes. We build that lead time into our sprint plan rather than discovering it mid-sprint.
  • Confirmation that this phase is dev only, with QA and prod added later. Scribl decision That scopes our environment plan and keeps us off prod work we would have to redo.

If a constraint on Scribl's side rules one of these out, send back the version that works. Adjusting the plan now is cheap. Finding out after we have built against the wrong account is not.

Runbook, GitHub and the deploy trust

What Scribl said

The kickoff covered where code lives, and it did not cover GitHub at all. Nobody asked whether Scribl has a GitHub organisation, so nobody answered. What was settled is the ownership arc.

"It probably makes sense for you guys to own everything now and then it's a handoff at some point." -- Matthew Kaplan, 00:59:44

Our code starts in Bounteous repositories, as agreed in the kickoff. Nothing on this tab blocks this week. It is here because one thing we found may change where the code starts, and that is worth asking about early.

Our initial research

We read the B2B source Eric sent. The git remote is Bitbucket, hs2studio/scribl-b2b, and there is no bitbucket-pipelines.yml anywhere in the tree. Every piece of CI in the repo is GitHub-only tooling, under .github/:

  • workflows/deploy.yml is a live GitHub Actions deploy. It runs on workflow_dispatch with an environment choice of QA or Stg, takes id-token: write, and uses aws-actions/configure-aws-credentials@v4 to assume secrets.AWS_QA_ROLE_ARN or secrets.AWS_STG_ROLE_ARN. It deploys the CDK stacks Scribl-Poc/Infrastructure and Scribl-Stg/Infrastructure into us-east-1. The named secrets and named stacks make this a real OIDC trust rather than a sample workflow. Whether it still runs is the part the files cannot tell us.
  • workflows/pr.yml gates pull requests on a label, an assignee, and a Jira-prefixed title, through actions/github-script on pull_request events.
  • workflows/linting.yml runs lint on pushes to main and dev and on every pull request. Its client test step is commented out with a note to add e2e tests later.
  • dependabot.yml schedules weekly updates for GitHub Actions and for the client and infrastructure package trees. Dependabot runs on GitHub and nowhere else.
  • A pull request template.

Here is the possibility, and it is a possibility rather than a finding. Dependabot, pull_request triggers, GitHub secrets and GitHub OIDC do nothing outside a GitHub repository. So a GitHub organisation with a working Actions-to-AWS trust may already exist for this product. If it does, and if it is Scribl's, this engagement may be able to build inside it from the start rather than transferring at the end, which is the cheaper end of the handoff Matthew described.

Two things stop us calling it more than a possibility. The client has not confirmed any of it. And the files cannot tell us whose organisation ran them. The pull request template links its tickets to a third-party Atlassian domain that is not Scribl's, which fits an earlier build vendor's organisation as comfortably as it fits Scribl's own. The git history in our copy is a Bounteous import dated 2026-08-25 and tells us nothing about origin. The file contents are the whole of the evidence, and they support the question, not the answer.

One more thing to reconcile rather than to argue about. Their pipeline deploys to us-east-1. Our POC database is in us-east-2.

On the OIDC trust itself, so nobody starts from zero. A GitHub Actions run exchanges a short-lived token for AWS credentials, so no long-lived AWS access key is ever stored in the repository. The identity provider is created once in IAM, and the B2B account very likely has it already. The deploy role's trust policy has to pin the subject claim to the organisation, the repository, and the branch or environment, because a policy that does not pin them lets any workflow in any repository on GitHub assume the role. The role ARN is handed to the workflow as a secret, one per environment, which is the pattern deploy.yml already uses. And the workflow needs id-token: write, which is the line people forget; without it the role assumption fails with an error that reads like a trust-policy problem when it is not.

What we are asking Scribl for

One question first, answered by a named person on a date. Is there a GitHub organisation for Scribl, who administers it, and do the B2B app's workflows still run in it? "We did not know we had one" is a perfectly good answer, and it is the one we would bet on. Either way the answer decides the next question, so it is worth five minutes with whoever set up the B2B build.

If the answer is yes, we want a decision on whether the D2C app can start in that organisation rather than move into it later, and with it four things Scribl owns:

  • A team for us in the organisation, or per-repo collaborator access. A team is easier to revoke, because removing one team removes everyone from every repo at once. Collaborator access has to be cleaned up repo by repo, so it drifts.
  • The branch protection and required-reviewer rules Scribl wants to live with. Tell us the rule and we work inside it.
  • A fresh repo rather than an existing one. That is our recommendation, because the D2C app shares no code with the B2B product, and a fresh repo keeps the two histories, access lists and CI configurations independent.
  • The AWS account id the deploy role lives in, and the name of whoever can create an IAM role there.

Once we have that, we send our GitHub handles for invitations, stand up the deploy role and trust policy with Scribl's IAM owner, and wire our pipeline to it. Our own deploys will gate on typecheck, lint, test and a build before they run, which is a choice about our pipeline rather than a comment on theirs.

If any of this cuts across how Scribl runs its estate, tell us the shape that works instead. An answer we can plan against is what we are after.
