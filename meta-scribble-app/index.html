scribl -- the project brain

What this repo is, and how to talk about it. Open this file first.

What it is

This repo is meta-scribl-app. It is not the app. The app is a separate repo, hs2studio/scribl-app on Bitbucket. This one is everything around the app, and it does three jobs.

A wiki

A VitePress site under docs/. Rendered, navigable, searchable. You run it locally with two commands.

A brain repo

Knowledge-vault conventions: raw capture in inbox/, research and meetings in knowledge/, reusable learnings in patterns/.

The delivery workspace

The board, the stories, the roadmap, the ADRs, the handbook. Delivery runs out of here, not out of a slide deck.

All three live in one repo so they cannot drift. The wiki is generated from the same files delivery edits. When a story moves, the site moves with it.

Four folders are the single source of truth for the doc site: product/, tracking/, handbook/, and knowledge/. Everything under docs/ is generated from them. Never hand-edit a generated page. Edit the source and re-run the sync.

reviews/ and other internal-only material -- raw transcripts, the team roster, research digests -- are named in the exclude list in scripts/docs-sync.mjs and stay repo-only. The rendered wiki is client-safe by construction; internal working material stays in the repo and out of the render.

Why it exists

Because the answer to "what did we decide, and where is that written down" should take one search, not a thread hunt. On most engagements the spec is in a doc, the decisions are in Slack, the board is in Jira, and the status is in whatever deck went out last. They disagree within a week and nobody notices until a client meeting.

Here the plan, the decisions, the board, and the process are files in one repo, and the wiki is generated from those same files. A page cannot go stale on its own. If the site says something wrong, the source said it wrong, and that is fixable in one place.

Day to day that buys you three things. You can answer a client question from the repo. You can see what is in flight without asking. And you can tell a new person to read three files instead of sitting through an hour of context transfer.

What we do with it

Things land here and things come out of it.

  • In -- meeting and call transcripts, research, client source material, and raw capture that has nowhere else to go yet. Decisions get written down as ADRs when they are made, not reconstructed later.
  • Out -- the rendered wiki, the board that says what is in flight, the stories the build runs against with their acceptance criteria, and the handbook that says how we operate in front of the client.

The loop is small. Capture it, route it to the folder that owns it, re-run the sync, and the site is current. Stories move across the board as the work moves, in the same change as the work.

How to use it

Three files, in this order, and you are oriented. product/overview.md is what scribl is in one page plus the engagement contract. tracking/board.md is what is in flight right now. handbook/ is how we work, covering definition of ready, definition of done, ceremonies, estimation, and how we operate in front of the client.

When you need to know why the stack is what it is, read the eleven ADRs under product/inputs/reference/decisions/, numbered 0001 to 0011. React Native as the primary target. Serverless-first backend with Fargate for the AI pipeline. Aurora Serverless v2 on PostgreSQL as the system of record. AWS CDK in TypeScript for all infrastructure. Skia for the drawing canvas. Submit-to-unlock enforced at the data and API layer. The AI pipeline as a separate async service that submit never blocks on. A provider-abstraction layer for Claude. Analytics on its own pipeline. Model tiering.

How to start the wiki locally

Node 22 or newer. Nothing else to install and no database.

npm install
npm run docs:sync    # render product/, tracking/, handbook/, and knowledge/ into docs/ pages
npm run docs:dev     # local preview with hot reload

The commands available to you

These are Claude Code slash commands and skills defined in .claude/. They work as soon as you open this repo in Claude Code. No setup.

Knowledge commands

  • /ingest -- ingest a URL into the knowledge wiki, or route a meeting transcript into knowledge/meetings/.
  • /ingest-standup -- ingest a call or standup transcript into knowledge/meetings/ and extract suggested action items. A human promotes those to stories.
  • /query -- ask a question against the knowledge wiki and get a cited answer.
  • /remote-ingest -- ingest one or more URLs and ship each as its own merged PR.

Work-item commands, the story and AC kit

This kit governs how a work item goes from a backlog line to filed, verified, and done.

  • /start-work-item -- picks the next ready work items, checks them for collisions, gates once on a human, then launches one scoped session per item in its own worktree. Reports only until the gate.
  • acceptance-criteria-lock -- binds a session to the work item's acceptance criteria verbatim, so it keeps going until every criterion has evidence and stops the moment they all do.
  • ears-acceptance-criteria -- puts each criterion into one of the six EARS forms with a machine-runnable verification line, so done is checkable without a judgement call.
  • scope-checkpoint -- binds a session to the item's declared scope and out-of-scope lists, so parallel sessions cannot collide.
  • adversarial-spec-review -- five personas review the item in parallel and return a verdict, catching thin acceptance criteria while they are still cheap to fix.

The Jira filing pipeline

Under scripts/jira-sync/. It turns a markdown story file into a filed Jira epic with its stories. Run through node scripts/jira-sync/jira-sync.mjs <command> <file>.

  • preflight -- parses the file and validates every parser and content rule. Exits clean only when there are zero errors.
  • dry-run -- prints the full creation plan as readable text. Never touches the network.
  • create -- files the epic and its stories, but only with an explicit --execute. Without it you get the dry-run plan again.
  • attach -- attaches local files referenced from the story descriptions to the issues created earlier. Also gated behind --execute.

Two rules on this pipeline, and they are not negotiable. Every write is gated behind --execute after a dry run. And no agent ever creates, edits, or transitions a Jira issue on its own. Stories are drafted to markdown for human review first, and the filing step is gated by a human.

Production stories live on the Jira board with project key SCRIBL. The mapping conventions, the label scheme, and the sync-back rule are in tracking/jira-board.md. POC stories, the S- numbered ones, stay in this repo and are not imported.

Subagents

Defined in .claude/agents/ and invoked by name. Four maintain the wiki: wiki-ingestor, wiki-querier, wiki-linter (finds orphan pages, broken links, stale content), and wiki-refresher (updates pages whose upstream source has moved on). Two handle Android builds: android-native-build and android-emulator. One, entire-search, searches this repo's checkpoint and session history.

Putting the commands to work

The lists above say what each command is. This says what you actually run when a real task lands on you.

You changed a source file and the site needs to catch up

Edit the file under product/, tracking/, handbook/, or knowledge/. Never the rendered page under docs/.

npm run docs:sync    # re-render the pages
npm run docs:dev     # eyeball it locally
npm test             # the content guard and the prose normalizer

Then run the wiki-linter subagent. It finds orphan pages, broken links, and content that has gone stale, which is exactly the damage a hand edit leaves behind. Fix what it reports before you push. npm run docs:build is the CI gate, so if it fails locally it fails in the pipeline too.

A Teams call just ended and you have the transcript

Run /ingest-standup and hand it the transcript. It writes the meeting into knowledge/meetings/ and pulls a suggested-action-items section out of the discussion. Those are suggestions. A human reads them and promotes the real ones to tracking/stories/; the command never creates a story on its own.

For a link rather than a transcript, an article or a vendor doc worth keeping, use /ingest. It snapshots the source, then writes source and entity pages into the wiki and updates the index. /remote-ingest does the same for a batch of URLs and ships each one as its own merged PR.

You need an answer out of the brain

/query reads the wiki index, pulls the pages that matter, and answers with links back to the source. Ask it the question you would otherwise ask in Slack.

/query what did we decide about the system of record, and why
/query what is in flight right now and what is blocked
/query what has the client asked for that is not in the MVP scope
/query brief me for tomorrow's design review: open questions and recent decisions

Prepping for a client meeting is the case it earns its keep on. Ask it for the open questions and the decisions since the last call, then read the pages it cites rather than trusting the summary. If it cannot find something, that is a real signal that the thing was never written down.

You are picking up a work item

/start-work-item picks the next ready items, checks them against each other for collisions, gates once on a human, and then launches one scoped session per item in its own worktree. Inside that session the first two moves are acceptance-criteria-lock and scope-checkpoint, which pin the session to the item's criteria and its declared file scope.

If the item's acceptance criteria look thin, run adversarial-spec-review before writing code. Five personas review it in parallel and return a verdict, and fixing a vague criterion in refinement is far cheaper than discovering it at review.

You shipped something in the app repo

The story lives here, so the same change has to land here too. Update tracking/stories/S-*.md. Move its status across the board states in tracking/board.md, check off the acceptance criteria that are now satisfied, and run npm run docs:sync. This is the pairing that keeps the wiki from drifting away from what actually shipped, and it is not optional.

How to talk about it

"It is the project brain for scribl. One repo holds the spec, the decisions, the board, and the process, and the wiki is generated from those same files, so the documentation cannot fall out of sync with what we are actually building."

If someone pushes further, the useful next lines:

  • Not Confluence, because the wiki is generated from the working files. A page cannot go stale without the underlying story going stale too, and that is visible on the board.
  • The decisions are eleven ADRs under product/inputs/reference/decisions/. The stack is decided and written down. Point at the ADR rather than reopening the argument.
  • A work item carries acceptance criteria, a declared scope, and an explicit out-of-scope list. If it is missing any of the three it is not ready, and we ask rather than invent.
  • The POC is a thin slice of the production target, not a throwaway. The production backend plan and the future-scale track are already written in tracking/.

Read product/overview.md for the one-page version of what scribl is, then tracking/board.md for what is in flight, then handbook/ for how we work. That is the whole orientation.
