## Context

The decision register (7.1) settled that under-13 users are a supported
audience and that COPPA compliance is a build requirement, not later
preparation, and named the governing ADR as the highest-priority outstanding
item. No ADR was written. In the meantime, implementation in `scribl-mobile-app`
proceeded on a provisional design so the rest of the build was not blocked on
it, and several source comments in that repo say so directly, for example
`apps/mobile/src/lib/account-class.ts`: "Pankaj's COPPA ADR is pending and may
add jurisdictions", and `packages/contracts/src/entities/consent.ts`: "the real
method comes from Pankaj's pending COPPA ADR." This ADR exists to catch the
record up to the code, not the other way round, and to name what the code
deliberately leaves open.

## What is already built

- **Age boundary.** `COPPA_AGE_THRESHOLD = 13` (`account-class.ts`). An account
  is classed `adult`, `minor` or `unknown` from date of birth. `unknown`
  (unparseable or implausible input) is treated as `minor` everywhere
  downstream: the gate fails closed rather than granting the adult path on bad
  input.
- **The gate actually gates.** `canProceedToAccountCreation` returns true only
  for `adult`. A `minor` classification branches into a parental-consent flow
  before any account is created, it does not merely record the age and
  continue. Covered by an e2e test: "the age gate branches a minor into
  parental consent, not into an account."
- **Production currently declines to enrol minors at all.** `allowsMinorEnrollment(appEnv)`
  returns `false` for `prod`, `true` for `dev`/`qa`. The code labels this
  "OPTION A" in a comment, i.e. a deliberately named, reversible stance rather
  than an oversight: the age-gate and account-class model are built and
  exercised in dev/QA, but no production account can enrol as a minor today.
  **This is a materially different posture from register 7.1's "under-13
  users are in scope."** Right now, in production, they are not yet.
- **Consent is versioned rows, per register 7.2**, with a `method` field
  (`self`, `stub`, `payment_instrument`, `signed_form`, `video`,
  `knowledge_based`). Only `self` and an explicitly-named `stub` are
  meaningful today; the four COPPA-approved verification methods are declared
  in the type but none is implemented. The `stub` value is deliberately
  visible in data rather than disguised as a real method, so a placeholder
  consent can never be mistaken for a verified one downstream.
- **Diagnostics and crash-reporting collection are gated on consent, fail
  closed.** `diagnostics-consent.ts` enforces, in order: an `unknown` account
  collects nothing; a `minor` needs both a `parental` consent row and the
  diagnostics consent row; a flag can only subtract collection, never grant
  it; an unreachable consent/flag provider means collection is off. Crash
  reporting (register 6.5) starts disabled and is enabled only after consent
  is recorded.
- **Parental-consent UI exists**: `ParentalConsentScreen`, `ParentControlsScreen`,
  `RequiredConsentGate`, wired at `app/(auth)/parental-consent.tsx`.

## Decision

Confirm register 7.1 as the standing product decision: under-13 users are a
supported audience and COPPA compliance is a build requirement. The age-gate
mechanism above, including its fail-closed defaults, is accepted as the
correct shape and should not be re-litigated as part of closing this ADR.

**Production stays on OPTION A (no minor enrollment in `prod`) until the two
open sub-decisions below are closed.** This is the one place the register and
the shipped code currently disagree, and OPTION A, not the register wording,
is what is actually live. Flipping it to allow minor enrollment in production
is a deploy-configuration change once the sub-decisions close, not a rebuild.

## Open sub-decisions (not resolved by this ADR)

These are the two questions register 7.1 already flagged as needing the
governing ADR to answer. Drafting this ADR from the code does not answer
them, because the code does not know the answer either: it stops at a `stub`.

1. **Store category.** Do we target Apple's Kids Category / Google Play
   Families policy, or serve under-13 users outside a children's category?
   These are different compliance regimes with different third-party-SDK
   rules (code-questions.md A9's log-retention numbers and the Crashlytics
   vendor question in code-questions.md section "1c" both wait on this).
2. **Verifiable parental consent method.** Which COPPA-approved method
   (payment instrument, signed form, video verification, knowledge-based
   authentication) is actually implemented. Until one is, `stub` is the only
   method the system can honestly record, which is why production does not
   enrol minors yet.

## Consequences

### Positive
- The build was not blocked waiting for this ADR: the mechanism, the
  fail-closed defaults and the UI exist and are tested.
- The record and the code now agree on what is actually live in production
  today (no minor enrollment), instead of the record describing a state the
  code has not reached.

### Negative
- Register 7.1 reads as "under-13 in scope," which could be presented to the
  client as more done than it is. Anyone quoting 7.1 without this ADR's
  production caveat overstates the current state.
- The two open sub-decisions still gate the launch decision on store category
  and retention (code-questions.md A9), so this ADR narrows what is open
  without closing the build-blocking item.

### Risks to monitor
- `allowsMinorEnrollment` is the single switch that matters. It must not be
  flipped to allow minor enrollment in `prod` before a real verification
  `method` exists, or the system starts recording `stub` consent for real
  under-13 accounts, which is the exact checkbox-consent failure the type
  design was built to make visible and prevent.
