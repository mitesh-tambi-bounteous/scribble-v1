Apple: the longest lead time, so it starts today

Scribl has no Apple accounts. Eric Rice, 00:48:15: "We don't have anything." Eric offered to do the work himself if we point the way (01:02:47). This is the pointing.

The order matters. Step 1 can take up to five business days on its own, and nothing else can start until it lands. Everything after it is hours, not weeks.

Step 1. Get a D-U-N-S number for Scribl

  1. A D-U-N-S number is a nine-digit business identifier issued by Dun and Bradstreet. Apple uses it to confirm Scribl is a real legal entity. Apple requires one for any organisation enrolment.
  2. Scribl may already have one. Check first with Apple's own lookup at developer.apple.com/enroll/duns-lookup before applying for a new one.
  3. If there is none, Apple's lookup offers to submit the request to Dun and Bradstreet at no cost. Apple's guidance: allow up to five business days to receive the number.
  4. Three things must match the legal entity, not the brand. Legal entity name, legal address, and a contact who can confirm both. A DBA, trade name, fictitious business name or branch is not accepted.
  5. The person who enrols must have legal authority to bind Scribl to agreements: owner, founder, executive team member, senior project lead, or an employee given that authority in writing by a senior employee.

Step 2. Enrol in the Apple Developer Program as an organisation

  1. Enrol as an organisation, not as an individual. An individual account cannot carry Scribl's name on the App Store listing and cannot hold team members under one entity.
  2. Apple asks for: the D-U-N-S number, the legal entity name and address, a website on Scribl's own domain, and confirmation of the enroller's authority. Apple may call the listed number to verify.
  3. Enrolment runs either on the Apple Developer app on an iPhone or iPad, or on the web. The app route is generally faster because identity verification happens on-device.
  4. The account must sit under a Scribl-owned Apple Account, not a personal one. Use a shared mailbox Scribl controls, for example an alias that survives any one person leaving.

Step 3. Who holds what, and what can move later

"This takes up to two weeks" does not mean we stop. None of the following needs an Apple account.

  • Internal device testing through Expo Go and development builds signed with a free personal team.
  • Every backend and data task, including the prompt-of-the-day pipeline and stroke storage.

AWS: they have an account, we need a structure we can grow into

Read this tab as our architecture ask, not as a copy of what Scribl runs today. Their B2B deployment tells us an AWS account exists and who might own it. It is not the design we build against. We are asking for a structure that starts small this phase and takes more environments later without being rebuilt.

What exists today, as context only

Eric Rice confirmed at kickoff that Scribl has an AWS account hosting the B2B game (00:45:38). The source Eric sent shows that product deploying two stacks to us-east-1 from GitHub Actions, with credentials from an assumed role rather than stored keys (.github/workflows/deploy.yml:26,41,49).

Three things we take from that and nothing more. An account exists, so this is a question of access rather than of standing something up from zero. Their region is us-east-1, which our region choice has to reconcile. And the credentials that reach that account live as GitHub secrets in a GitHub organisation whose owner we have not confirmed, which is why the GitHub tab is part of this ask. We are not adopting their stack layout, their environment names, or their pipeline.

The thing to be careful about. We cannot tell from the source whether QA and Stg are two AWS accounts or two stacks in one account, and no account id appears anywhere in the repository. So do not assume Scribl already has environment separation at the account level. Ask.

What we need the account structure to do

This phase is dev only, agreed at kickoff (Rob Forshier II, 00:54:17). QA and production come later. So the structure has to be right for one environment now and for three or four later, without a migration in the middle.

  1. One environment per boundary, not one account with everything in it. Dev, QA and production each need their own isolated set of resources. A change in dev must not be able to reach production data, and a production incident must not be debugged by someone with a dev credential.
  2. Sized independently. Dev is small and slow on purpose: minimum instance sizes, no multi-AZ, short backup retention, no read replicas. Production is sized for real load and real recovery targets. The environment definition has to carry its own sizing rather than inherit a single default, so turning up production is a config change and not a rewrite.
  3. Repeatable from code. One infrastructure definition, parameterised by environment, so adding QA later is a new parameter set rather than new hand-built resources.
  4. Separate credentials per environment. One assumable role per environment, so access to dev never implies access to production, and revoking one does not touch the others.
  5. Cost visible per environment. Whoever pays needs to see dev and production separately from day one.

How access gets granted, and what each option does to the above

OptionWhat it meansAgainst the five points
A. Separate accounts inside Scribl's AWS organisationOne account per environment, created under their organisation, each with a role we assume.Meets all five cleanly. Isolation is the account boundary, which is the strongest one AWS has. Cost splits itself. Scribl owns the asset from day one, so nothing migrates at handover. Slowest to approve, because it needs organisation-level rights.
B. One new account, environments separated inside itA single account we work in, with per-environment stacks, networks and roles.Workable, and faster to grant. C. A role inside their existing B2B accountScribl issues a scoped role in the account that already runs the B2B game.Fastest to get moving. Puts our workloads next to a live product, which is the one thing we would rather not do, and it gives us no path to a separate production environment later. D. A Bounteous-owned accountWe stand it up ourselves this week.Zero waiting and zero risk to their estate. The cost is a real migration at handover, including data. Use it only if their approval runs long.

Our recommendation: A, with D as the unblock. Separate accounts per environment under Scribl's organisation is the structure we would design for this application regardless of what exists today. Start with one account, dev, created in that pattern so QA and production are additions rather than a redesign. If organisation-level approval takes more than a week, we start in a Bounteous-owned account so the build does not wait, and we plan the move.

Region

Decide it with the account, not after. Our POC database is in us-east-2 and Scribl's B2B stack is in us-east-1. That matters for latency between anything the two products ever share, for cross-region data transfer charges, and because infrastructure code pins a region and is not trivially moved once data lives there. Our recommendation is us-east-1, matching Scribl, and we move our POC data.

The finding, hedged

Whitespectre is not a Scribl domain. Eric referred to the original build vendor on the kickoff call by name (00:55:50), and the Jira host in the pull request template is that vendor's. So the GitHub organisation that runs these workflows may belong to the previous build vendor rather than to Scribl.

This is the question to ask, not a fact we have established. Two readings both fit the files. The organisation is the vendor's, and Scribl has never had access. Or the repository is Scribl's and only the Jira instance was the vendor's, which is a normal thing to find after a vendor engagement. The files cannot separate those, and our copy of the history is a single import commit, so it tells us nothing about origin.

Why this matters more than repository access

Those AWS role ARNs are stored as GitHub secrets in that organisation, and deploy.yml uses no GitHub Environment protection, so they are repository-level secrets. Read plainly, whoever administers that GitHub organisation holds the credentials that deploy to Scribl's AWS account, and anyone who can trigger the workflow can deploy to Staging.

If the organisation is the previous vendor's, then a third party currently holds the deploy path to Scribl's live B2B product. That is worth raising with Scribl regardless of what it means for our project. It is also the reason we are not asking to reuse their trust: we would be asking someone else for it.

One more thing the files cannot tell us. Whether QA and Stg are two AWS accounts or two stacks in one account. There are two role ARNs, which is good practice either way, but nothing in the repository names an account id. That question belongs to the AWS tab.
